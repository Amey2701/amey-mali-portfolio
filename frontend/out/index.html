Problem — The engineering context.

A media platform needs to show and manage thousands of title records. Users need to browse them in a clear interface, and that interface needs a dependable API behind it to fetch and update the data.

Approach — Clear responsibilities. Connected layers.

The platform uses React for the interface, Node.js with Express for the API, and MongoDB for application data. My work sat at the two ends of that chain: building and fixing screens on the frontend, and adding or adjusting endpoints on the backend.

My scope of work

  • Building and fixing React UI components
  • Connecting screens to the API with fetch calls
  • Writing and updating Express REST endpoints
  • Basic MongoDB queries for title records
  • Form validation and error states
  • Bug fixes and code-review feedback via Git

Challenges & solutions — Where the engineering happens.

01 / Showing a large list of titles clearly
Challenge
With thousands of titles, a screen that loads everything at once feels slow and is hard to scan.
Implementation
Built list views in React that request data in smaller pages from the API, with loading and empty states.
Trade-off
Paging keeps screens fast, but needs the frontend and backend to agree on how pages are requested.
02 / Keeping frontend and API in sync
Challenge
When an endpoint response changes, the screens that use it can break without warning.
Implementation
Wrote and adjusted Express endpoints, then updated the matching React calls and checked the responses by hand.
Trade-off
Small, consistent response shapes are easier to consume, but changing them means updating every screen that relies on them.
03 / Handling bad input and failed requests
Challenge
Forms and API calls fail in ordinary ways: empty fields, wrong formats, a server that doesn't respond.
Implementation
Added validation on the form and on the endpoint, and showed readable error messages in the UI.
Trade-off
Validating in both places repeats some logic, but the server must never trust the browser alone.
